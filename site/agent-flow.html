AgentFactory · how the loop works — backlog → board → back

A single-user local task board: humans create & review work in the web UI, an external agent (Claude Code or any MCP client) consumes and progresses it. The two sides never talk directly — a shared SQLite file is the only channel. This page covers both halves: first the consumer loop (how an agent claims, works and submits a task), then the producer side — where tasks come from when they aren't hand-written on the board.

    4 · Producers: the round trip

    Tasks don't have to be hand-written on the board. A producer is an agent that watches a source of work — here Azure DevOps, via ado-bridge — claims items, turns them into implementable specs with claude -p, queues them as AgentFactory tasks, and reflects every status change back to the source.

    5 · One work item, end to end

      6 · Marker-driven & self-healing

      🔑The title is the dedup key. Tasks are titled AB#123: …; before creating anything the bridge checks the board for that prefix. Re-running a pass can never duplicate work.
      🏷️Tag last, recover first. The ADO item gets agentfactory · AF:<key> as the final inbound step. An item claimed but not yet tagged (crash mid-pass) is re-selected by a recovery clause and resumed — no state file anywhere.
      🤝Rev-safe claims. The assignment PATCH carries a test op on the item's rev — if a human touched the item concurrently, the human wins and the bridge skips it.
      ♻️Idempotent outbound. The bridge only moves items whose state it set itself, and skips items already in the target state. Manually moved items are left alone; closing twice is a no-op.
      ⚙️Per-repo onboarding in one command. Run-AdoBridgeLoop -Init scaffolds the config, the worker wiring, the gitignore entries, and registers the workspace on the board.
      cd c:\git\your-repo Run-AdoBridgeLoop -Init # scaffold + register workspace Run-AdoBridgeLoop -StorePat # PAT → Credential Manager Run-AdoBridgeLoop -DryRun # sanity check, mutates nothing # daily use — the three ado-bridge loops: Run-AdoBridgeLoop # A: producer Run-AgentFactoryLoop # B: consumer Run-ReviewerLoop -Reviewer claude # C: reviewer (or codex) # (or AgentFactory's dispatcher as the consumer: # one fresh headless session per task)
      🎚️Process templates are config. Agile (New → Active → Resolved → Closed) out of the box; Scrum or custom flows are a few state names in ado-bridge.config.json. requiredTag makes import opt-in per item (e.g. #ai-agent).

      7 · Any source can be a producer

      ADO is the first adapter, not the design. A producer is any agent that can honour the contract:

      1.Stable dedup key in the task title (AB#123:, GH#456:, JIRA-789: …) so passes are idempotent.
      2.A design pass — raw items become implementable briefs (spec + acceptance criteria) before they're queued; the producer is an agent, so this is where it earns its keep.
      3.Queued task via the HTTP API — the board stays the single human checkpoint regardless of where work originates.
      4.Status reflected back — review and done flow to the source (comment + close in ADO today). The PR itself needs no producer step: the worker's finish protocol opens it automatically from the pushed branch, and the board's watcher closes the task when it merges with green checks.
      Azure DevOps Boards · shipped GitHub Issues Jira ServiceNow support mailbox monitoring alerts

      The board also accepts a second intake shape today: pr-review tasks — a teammate's GitHub or Azure DevOps pull request imported as a task that is reviewed, never implemented (born straight into In Review; "Mark reviewed" closes it and copies your verdict as clean markdown for the PR).

      Same board, same review gate, same worker loop — only the intake adapter changes. See the system overview for how multiple bridges and workspaces compose.
